## PR #6 사용성 통합

- PR #6의 공강 클릭 타임라인과 카드 넘기기 방식을 현재 main의 추천 API에 연결했습니다. 09~20시 축의 공강이나 아래 버튼을 누르면 출발 시각을 채우고 추천합니다. 버튼·좌우 키·가로 밀기로 상위 3개 카드를 넘깁니다.
- 시간표는 기존 앱의 F3 `meal_context` exporter를 사용합니다. 휴강을 제외하고 겹친 수업·시험·일정을 합쳐 공강을 찾으며, 다음 강의실을 확인할 수 없으면 해당 공강의 자동 추천을 비활성화합니다. 개인정보를 저장하는 별도 시간표 파일은 만들지 않습니다.
- 지도 배경은 PR #6의 `1f238c8`에 포함된 `data/osm/basemap.json`을 사용합니다. 길·건물·녹지·물만 그리고 추천 식당을 별로 표시하며, 별을 누르면 해당 카드로 이동합니다. 지도 타일을 외부에서 받지 않습니다. 추천·도보 계산은 main의 기존 공개 식당 데이터와 보행망을 유지합니다.
- Windows 배포에는 기존 `meal/`, `web/` 수집 규칙으로 새 타임라인 모듈과 UI 파일을 함께 포함하고, 지도 JSON도 필수 공개 자료로 포함합니다. CA2 및 사용자 조사 입력의 저장 위치는 기존 구조를 사용합니다.
- 평가 보고서의 `inputSha256`은 UTF-8 텍스트를 LF로 정규화한 해시입니다. Git의 LF/CRLF 변환에 따른 차이를 제거하며, 입력값 변경은 계속 검출합니다. 실제 사용자 입력의 revision/hash 계산은 변경하지 않았습니다.

화면 검사(데스크톱 빌드용 Python 환경과 Playwright Chromium 필요):

```bash
python campus/CA1_Meal_agent/tests/browser_smoke.py --output /path/to/test-results
```

## 고기 메뉴의 1인 예산 기준 (2026-11-12)

고기 주메뉴는 게시된 **1인분 가격을 그대로 1인 예산**에 적용합니다. 중량만 적힌 메뉴도 기본 제공 단위의 가격을 사용하고, 최소 주문량을 임의로 곱하거나 중량으로 가격을 나누지 않습니다. 여러 명용 세트·족발 한 다리·사이드·추가는 구분합니다.

## 미확인 식당 정보 직접 입력

실행 중인 로컬 서버의 [식당 정보 입력함](http://127.0.0.1:8030/survey)에서 작성합니다. 추천 화면에도 진입 링크가 있습니다. 미확인18곳 중 메뉴·매장 가격이 필요한 곳은9곳, 요일별 시간이 필요한 곳은13곳이며 서로 겹칩니다. ‘식당별 미확인 항목표’에18곳을 모두 정리했고, 검색·식당가·필요 항목·저장 상태로 찾을 수 있습니다. 현재 목록 사본은 `data/survey/followup_2026-11-12/remaining_information.json`입니다.

1. 식당을 선택하면 **미확인 항목만 입력 폼에 표시**합니다. 메뉴·가격이 확인된 곳은 영업시간만, 시간이 확인된 곳은 메뉴·가격만 입력합니다. 기존 확인 내용은 참고 자료에서 볼 수 있습니다. ‘영업시간만’9곳 / ‘메뉴·가격만’5곳 / ‘둘 다 미확인’4곳 필터로 좁힐 수 있으며 정리표에도 같은 필터를 적용합니다.
2. 메뉴·가격·식사 분량 조건, 요일별 시간·휴무, 확인일·출처를 입력합니다. 가격을 모르면 빈칸으로 두고 메모만 남겨도 됩니다. 확인 체크는 확인일·방법과 실제 확인 근거가 있을 때 사용합니다.
3. **입력 내용 저장**을 누릅니다. `data/survey/user_entries/p_XXXX.json`에 서버 파일로 저장하며 새로고침 후 복원합니다. 저장 실패·다른 창의 동시 수정은 입력을 유지한 채 안내합니다.

입력함은 검토 전 초안입니다. 사용자가 작성한 파일을 후속 작업에서 검토해 기존 ID·attrs·출처 이력을 보존하면서 `data/places/`의 추천 데이터에 반영합니다. 페이지 저장만으로80곳의 추천 준비 수가 바뀌지는 않습니다. 나중에 입력 UI/API를 제거해도 **`data/places/`와 `data/survey/user_entries/`를 보존하면 저장한 정보는 남으며**, 이미 추천 JSON에 반영한 정보는 계속 사용할 수 있습니다. 화면 검증용 데이터는 `.local/survey-ui-test/`에 분리했습니다.

## 학사 시간표 자동 연동

시간표 JSON 업로드를 제거하고 기존 학사 앱이 저장한 시간표를 **자동 조회**합니다.
기본 데이터 위치는 개발 앱과 같은 `desktop/.dev-data`입니다. 식사 추천을 요청할 때마다 최신 저장 상태를 읽고,
화면 진입·날짜/시각 변경·화면 복귀 때 직전 수업 건물을 다시 조회합니다. 학사 앱이 꺼져 있어도 마지막 저장 내용을 읽을 수 있습니다.
연동 설정 패널과 성공 안내는 제거했고, 읽기 실패나 미등록일 때만 다시 확인·직접 입력 안내를 표시합니다.
학교 사이트에서 새 시간표를 수집하는 기능은 기존 학사 앱에서 실행합니다.
유니버스 앱에서 직접 입력한 시간표도 같은 저장소에 반영되므로 그대로 추천의 기준으로 사용합니다.

자동 연동에 사용하는 외부 변경은 사전에 사용자에게 보고한 F3 파일 세 개입니다.
`F3_Attendance_agent/attendance/meal_context.py`, `attendance/__main__.py`, `tests/test_meal_context.py`.
기존 `desktop/cli.py attendance campus-context --date YYYY-MM-DD` 명령을 CA1 서버가 호출합니다.
학사 DB는 읽기 전용으로 열며 로그인·성적·과목명·출결·메모는 결과에 포함하지 않습니다.
수업 시간·강의실·휴강/보강 판정만 메모리로 전달하고 시간표 사본을 파일로 저장하지 않습니다.

같은 과목이 오전·오후에 나뉘어 있는 경우에도 실제 시간 블록을 분리해 공강을 유지합니다.
사용자 시간표 수정·휴강 취소·학교 보강·직접 추가한 보강·교시 시간 설정을 기존 F3 규칙으로 반영합니다.
시간표 미등록·일부 미입력·읽기 실패는 수업 없는 날과 구분합니다. 이 경우 안내의 **직접 입력하기**로 수동 추천을 이용할 수 있으며, 다음 강의실 직접 지정은 항상 사용할 수 있습니다.
다음 수업의 강의실이 `온라인`·`비대면`·`원격` 등 명시적인 온라인 표기이면 수업 시작 시각은 유지하고,
다음 건물로 이동하는 시간은 0분으로 계산합니다. 이전 수업이 온라인이면 현재 위치를 추측하지 않고 출발 건물을 직접 선택하도록 안내합니다.

설치 앱 데이터를 읽으려면 CA1 서버 시작 전에 `CA1_ACADEMIC_MODE=app`을 설정합니다(`desktop/cli.py --app` 사용).
기본은 `dev`이며 데이터가 비어 있다고 다른 저장소로 자동 전환하지 않습니다.
기존 학사 런처와 동일하게 `F3_DATA_DIR`, `F1_DATA_DIR`, `F6_DATA_DIR` 환경변수로 명시한 경로도 따릅니다.

현재 로컬 개발 학사 저장소 확인(2026-11-11): 사용자가 입력한 **6개 과목의 시간표가 모두 연결**됐으며 `status=ready`, `missingTimetableCount=0`입니다.
파일 내보내기 없이 다음 추천 요청에 변경 내용이 반영됩니다. `공2-100`은 별관과 구분한 공과대 2호관 본관으로 연결합니다.

시간표 UI 정리 단계 검증: **CA1 전체 545개 테스트 통과**. 사용자가 저장한 실제 시간표로 자동 출발/다음 강의실 선택,
`공2-100` 본관 연결, 온라인 수업 시작 시각 유지, OSM 경로와 390px 모바일 화면을 API·브라우저에서 확인했습니다.
앞선 자동 연동 검증에서는 F3 전체 93개 테스트와 별도 임시 학사 DB를 이용한 오전·오후 사이 공강,
저장 내용 변경 즉시 반영, 직접 강의실 지정, 시간표 미완성 시 차단, JSON 업로드 제거를 확인했습니다.
실제 학사 저장소에 테스트 수업을 추가하지 않았습니다.

출발시간은 한국 현재 시각으로 채워진 **시간 입력**이며 날짜는 옆 달력에서만 바꿉니다. **지금**은 오늘·현재 시각으로 되돌립니다. 시간 글씨는 18px로 줄였습니다.
출발 건물을 비우면 선택 시각의 실제 직전 수업 건물 이름이 회색 placeholder로 보입니다. 날짜·시각을 바꾸어도 직접 입력한 출발지는 유지합니다.
예산은 **최소~최대 금액 직접 입력**과 빠른 선택 버튼으로 설정합니다. 양끝을 포함하고 한쪽 또는 양쪽 제한을 비울 수 있습니다.
범위 안 대표 식사 메뉴가 있는 식당만 추천하고 카드의 대표 가격도 해당 메뉴들의 중앙값으로 계산합니다. 사이드 메뉴만 맞는 식당은 제외합니다.
API는 `budgetMin`/`budgetMax`를 지원하며 기존 `budget` 상한 방식과 동시에 지정할 수 없습니다.
브라우저에서 현재 시각·달력·날짜별 건물 변경·예산 역전 입력 차단·실제 식당 범위 필터·OSM 지도와 320/390/768/1024px 화면을 확인했습니다.

## 모듈 계획

현재 추천 기준(2026-11-12): 네이버 재확인 목록 98곳 중 메뉴·가격과 요일별 영업시간이 모두 확인된 **실제 80곳**을 추천 대상으로 사용합니다.
좌석 규모·혼밥 가능 여부와 인원별 좌석 필터는 데이터·점수·이유 칩·API에서 제거했습니다.
식사유형이 없는 식당은 설정의 일반 식사시간 **30분**과 시간대별 예상 대기를 적용하고 `mealTimeEstimated: true`로 표시합니다.
이 계산 가정을 조사된 `attrs`로 저장하지 않습니다. 영업시간·이동시간·예산에 따라 실제 추천 수는 달라집니다.

화면은 기존 데스크톱 앱의 [`Paper & Pine 디자인`](../../univ_us_local/frontend/DESIGN.md)에 맞췄습니다.
같은 종이색·녹색·Pretendard 글꼴·헤더·카드 규칙을 사용하며 수정 파일은 `campus` 안에 있습니다.
추천 가능한80곳을 우선 보여 주고 활성98곳의 조사 목록은 전환해서 볼 수 있습니다. 제외된 과거 식당은 기본 목록에 표시하지 않습니다. 샘플·거리 비교는 개발 도구에 있습니다.

9곳 추천·UI 적용 당시 검증: 전체 테스트 **422개 통과**, 실제·샘플 데이터 오류 **0개**. 최신 전체 테스트 결과는 맨 위 네이버 재확인 절을 참고하세요.
샘플을 끈 점심 예제에서 실제 식당 **상위 3곳 + 추가 6곳**, 도보 **18구간 모두 OSM**을 확인했습니다.
당시 브라우저에서 시간표 가져오기·강의실 직접 입력·메뉴/시간 출처·9/100곳 목록 전환을 확인했고,
데스크톱 및 390px 모바일 화면에서 스크립트 오류와 가로 넘침이 없었습니다.
선정 목록 가져오기와 조사 적용을 재실행해 식당 100개 및 ID 대응표의 내용·수정 시각이 모두 유지되는 것도 확인했습니다.

| 모듈 | 하는 일 | 정의서 |

## 지키는 선

- `/v1/meal/recommend` 가 **유일한 계산기**다 — 식사 화면과 CA2 대화(`recommend_meal`)가 같은 함수를 부른다.
- 카카오 로컬 API 응답은 저장하지 않는다. 지도 링크는 카카오맵 검색 주소로 연다.
- 속성(가격대 · 영업시간 등)이 없는 곳은 추천하지 않는다.

### 초기 공공자료 100곳 선정·변환 (이력)

초기에는 전체 후보를 모두 등록하지 않고 **식사할 수 있는 밥집 100곳**을 선정했습니다. 현재 활성 명단은 맨 위 네이버 재확인 목록입니다.
[`meal/selection.py`](meal/selection.py)의 식사업종 허용 목록, 카페·편의점·술집 명칭 필터와 개별 검토 제외 목록을 적용하고,
같은 상호·주소·층의 중복을 선정 단계에서 제외합니다. 원천 `sourceId` 자체를 병합하지는 않습니다.
남은 후보를 **캠퍼스 경계 거리 `boundaryM` 오름차순 → sourceId 순**으로 정렬해 앞의 100곳을 고릅니다.
이 순서는 선정 우선순위이며 특정 강의실에서의 OSM 도보 시간이나 추천 순위가 아닙니다.

**최초 선정하거나 명단을 다시 검토할 때** 아래 명령을 실행합니다.

```powershell
.\.venv\Scripts\python.exe scripts/select_meal_candidates.py --limit 100 --dry-run
.\.venv\Scripts\python.exe scripts/select_meal_candidates.py --limit 100
```

선정 파일은 [`selected_candidates.csv`](data/survey/selected_candidates.csv), 원본 해시·선정 명단·제외 이유는
[`selection_report.json`](data/survey/selection_report.json)에 저장합니다. 원본 [`candidates.csv`](data/survey/candidates.csv)는 보존합니다.
공공 분류나 이름만으로 실제 영업 상태·식사 가능 여부를 확정할 수 없으므로 현장 조사에서 다시 확인합니다.

ID 예약을 먼저 저장하고 **각 파일을 원자적으로 교체**합니다. 폴더 전체를 한 번에 바꾸는 트랜잭션은 아니므로,

### 영업 구간과 라스트오더

점심·저녁의 라스트오더가 다르면 `hours`에 구간을 따로 기록합니다. 예를 들어 아래 가게는
14:30까지 점심 주문을 받고, 17:00부터 다시 저녁 주문을 받습니다.

```json
[
  {"days": ["월", "화", "수", "목", "금"], "open": "11:00", "close": "15:00", "lastOrder": "14:30"},
  {"days": ["월", "화", "수", "목", "금"], "open": "17:00", "close": "21:00", "lastOrder": "20:30"}
]
```

기존처럼 한 행에 `break`를 쓰는 경우, 그 행의 `lastOrder`는 **브레이크 이후 마지막 영업 구간**의 값입니다.
`break.end < lastOrder <= close`여야 하며, 브레이크 이전·도중 시각을 쓰면 데이터 검사와 계산 단계에서 거부합니다.

### 계산 설정 검증

[`data/settings.json`](data/settings.json)은 [`settings.schema.json`](data/schema/settings.schema.json)으로 검사합니다.
도보 속도·계수와 점수의 나눗셈 기준은 양수, 시간·가중치는 0 이상이어야 합니다.
전체 가중치 합은 양수여야 하며, 잘못된 필드·피크 시간 구간·NaN·무한대도 계산 전에 거부합니다.
가중치 합은 1이 아니어도 자동 정규화되며, 개별 가중치를 0으로 설정해 요소를 끌 수 있습니다.

### 혼잡과 전체 도보 점수

혼잡은 피크 시간의 학식을 대상으로 하는 추정 신호입니다. 좌석 규모에 따른 감점은 제거했습니다. 실측 혼잡도가 없으므로
`ranking.weights.crowd`를 **0.10 → 0.03**으로 낮췄습니다. 맑은 날 가중치를 정규화한 뒤의
최대 점수 차이는 약 **0.1111 → 0.0361**로 줄어듭니다. 피크 대기 시간은 필요 시간 계산에 계속 반영합니다.

거리 점수는 출발지에서 식당까지뿐 아니라 **식당에서 다음 강의실까지의 도보 시간**도 합산합니다.
`distanceZeroMin=15`는 편도당 기준이며, 두 구간을 이동하면 기준도 두 배로 적용합니다.

```text
전체 도보 = 출발지 → 식당 + 식당 → 다음 강의실
다음 강의실 있음: 거리 점수 = max(0, 1 - 전체 도보 / 30)
다음 강의실 없음: 거리 점수 = max(0, 1 - 편도 도보 / 15)
```

같은 건물로 돌아오면 기존 거리 점수와 같고, 다른 건물로 이동하면 실제로 계산에 사용하는 두 구간을 모두 평가합니다.
비가 오면 기존처럼 거리 가중치를 두 배로 높인 뒤 전체 가중치를 정규화합니다.
응답의 `totalWalkMin`과 `총 도보 N분` 이유 칩에도 합산 시간을 표시합니다.
`max_walk_min` 필터는 **출발지 → 식당의 편도 제한**입니다.
현재 추천의 기본 도보 시간은 아래의 OSM 보행 경로로 계산합니다. 경로를 찾지 못한 구간만
기존 직선거리·우회계수·분속 추정으로 대체하며 `walkRoutes`에 출처와 이유를 표시합니다.

### 추천 필터와 순서

```python
Filters(include=("일식", "중식"), required_tags=("채식 가능", "빠른 식사"))
```

이 요청은 **일식 또는 중식**이면서 **채식 가능하고 빠른 식사인 곳**만 남깁니다.
`include`의 음식 종류는 OR, `required_tags`는 모두 만족해야 하는 AND 조건입니다.
기존 `include=("일식", "채식 가능")` 입력도 종류와 특징을 나눠 같은 규칙으로 처리합니다.
`exclude`는 종류·특징 중 하나라도 일치하면 제외하며, 필수 태그에 음식 종류나 사전에 없는 값을 쓰면 오류를 반환합니다.

상위 3곳은 카테고리 다양성을 먼저 확보하고 부족한 자리를 채운 뒤,
선택된 후보를 **점수 내림차순 → 필요 시간 오름차순 → ID 순**으로 다시 정렬합니다.

## OSM 보행 경로와 시간표 연결 (구현 완료)

추천은 `출발 건물 → 식당 → 다음 강의실` 두 구간을 로컬 OSM 보행 그래프에서 각각 계산합니다.
`meal/routing.py`는 보행 가능한 길의 최단 경로와 양 끝의 보행망 연결 거리를 더하고,
`ceil(거리 / metersPerMin)`으로 시간을 구합니다. 경로 거리에는 우회계수 1.3을 다시 곱하지 않습니다.
보행 통행 제한·보행 일방통행·기록된 담장/교문을 고려합니다.

- 공개 보행망: [`data/routing/walk_network.json`](data/routing/walk_network.json), 보행 노드 31,484개·구간 36,559개.
- 건물 마스터: [`data/buildings.json`](data/buildings.json), OSM 건물 27곳. `공7`, `공7-223`, 건물 이름 또는 `위도,경도` 입력 지원.
- 출처/정밀도: [`보행망 설명`](data/routing/README.md). 건물 중심이나 등록 출입구에서 보행망까지의 연결 구간은 추정이며, 실내 이동·신호 대기·실시간 통제는 포함하지 않습니다.
- 보행망 누락·범위 밖·연결 단절은 `source: "estimate"`와 `fallbackReason`을 반환합니다. 추천 화면에서도 추정 대체를 알립니다.
- `rank()`와 `compute_for_place()`는 기본적으로 OSM을 사용합니다. 기존 방식은 `router=EstimateRouter()`를 전달합니다.
- 응답 `walkRoutes.to` / `walkRoutes.back`: `distanceM`, `durationMin`, `source`, `fallbackReason`, `connectorM`, `path`.

### 로컬 화면 실행

Windows에서는 이 폴더의 [`Start-Meal.cmd`](Start-Meal.cmd)를 실행하고 <http://127.0.0.1:8030>을 엽니다.
현재 작업 환경에는 전용 `.venv`와 의존성이 설치되어 있습니다. 새 환경은 다음 순서로 준비합니다.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m meal.api
```

1. 식사 시작 시각은 **현재 시간**입니다. 다른 날짜가 필요하면 옆 **달력**을 누릅니다. 시간표는 별도 설정 없이 자동으로 읽습니다.
2. 출발지를 비우면 회색 글씨로 표시된 실제 직전 수업 건물을 사용하고, 다음 강의실은 다음 수업에서 자동 선택합니다. 직전 수업이 없는 경우 출발지를 직접 지정합니다.
3. 다음 강의실을 **직접 입력**하면 지정한 장소가 시간표보다 우선합니다. 다음 시작 시각을 비우면 시간표의 시각을 유지합니다.
4. 시간표를 사용할 수 없으면 안내의 **직접 입력하기**를 누르고 출발지·다음 강의실·시작 시각을 입력합니다. 마지막 수업 뒤에는 **다음 수업 없음**을 선택합니다.
5. **식사 예산**에서 최소·최대 금액을 선택합니다. **전체**를 누르면 예산 제한을 해제합니다.
6. **식당 추천받기**를 누른 뒤 식당의 **이동 경로 보기**에서 실제 지도 위 경로를 확인합니다. 기존 거리와의 비교는 접힌 비교 도구에 있습니다.

휴강·제외 과목은 건너뛰고 보강을 포함합니다. 수업 중이면 연속 수업이 끝나는 시각부터 계산하며 화면에 알립니다.
미등록/모호한 강의실을 다음 수업 없음으로 처리하지 않고 직접 입력을 요청합니다.
건물 코드 일부는 OSM 이름에서 만든 내부 코드입니다. 등록되지 않은 별칭은 `data/buildings.json`에서 확인·추가하거나 좌표로 지정하세요.

사용자는 외부 학사 코드의 사전 보고 후 수정을 허용했습니다. 자동 연동은 위의 F3 읽기 전용 명령으로 구현하며
기존 학사 HTTP API의 인증 쿠키·세션 검사·CORS는 수정하지 않습니다. 예전 수동 내보내기 도우미
`scripts/export_attendance.js`와 합성 시간표 파일은 개발 자료로 남아 있지만 현재 화면에서는 사용하지 않습니다.

식당 샘플은 가짜 메뉴·영업 정보이므로 실제 가게 추천 시연으로 해석하면 안 됩니다.
API와 화면은 실데이터를 기본으로 쓰고, **개발용 샘플 식당 포함**을 체크하면 샘플을 포함합니다.
실제 식당은 웹 부분 조사 상태이며 필수 현장 검수 정보가 남아 있습니다. 샘플을 끄면 실제 명단·확인된 정보를 조회할 수 있지만,
메뉴·가격과 영업시간이 모두 확인된 식당은 `attrs.status: "partial"`이어도 추천합니다. 하나라도 미확인·상충이면 보류합니다.

API: `POST /v1/meal/recommend` (`at`, `autoTimetable` 기본 true, `origin`, `nextRoom`, `nextStart`, `noNextClass`,
`routeMode: "osm"|"estimate"`, `includeSamples`, `rain`, `budget`) · `GET /v1/meal/timetable?date=YYYY-MM-DD`(개인 수업 블록을 제외한 연동 요약)
· `GET /v1/meal/places` · `GET /v1/meal/places/{placeId}` · `GET /v1/buildings`.
요청 예시와 상세 형식은 실행 후 <http://127.0.0.1:8030/docs>에서 확인할 수 있습니다.

### 실제 지도 배경과 경로 표시

API 키 없이 사용하는 **OpenStreetMap 배경 + Leaflet 1.9.4** 지도입니다. 배경은 온라인으로 불러오고,
보행 경로·시간은 기존 로컬 OSM 보행망에서 계산합니다. 경로 좌표는 `[위도, 경도]`입니다.
출발 → 식당과 식당 → 다음 강의실을 다른 색으로 표시하고, 위치 마커·구간별 거리/시간·확대/축소·전체 경로 보기를 제공합니다.
다음 수업이 없으면 식당까지의 구간만 표시하며, 보행망을 찾지 못해 직선 추정한 구간은 점선으로 구분합니다.
배경을 읽지 못하면 안내와 경로 도식을 보여 줍니다. 실시간 위치 추적이나 음성 내비게이션 기능은 아닙니다.

Leaflet 라이브러리·스타일·이미지·라이선스는 [`web/assets/leaflet`](web/assets/leaflet)에 고정해 보관합니다.
버전·출처 URL·SHA-256은 `VENDOR.json`에 있습니다. 지도 타일은 브라우저가 현재 화면에 필요한 것만 요청하고
기본 HTTP 캐시와 Referer를 사용하며 지도에 출처를 표시합니다. 일괄 수집·오프라인 타일 저장은 하지 않습니다.
공개 배포나 트래픽 증가 시에는 [OSM 타일 이용 정책](https://operations.osmfoundation.org/policies/tiles/)에 맞는 공급자를 선택해야 합니다.

네이버지도는 지도 배경과 길찾기가 별개입니다. [공개 Directions 5 API](https://guide.ncloud-docs.com/docs/application-maps-direction5-api-vpc)는 자동차 경로만 제공하므로
이 프로젝트의 도보 계산을 대신하지 않습니다. 나중에 Maps용 API Key ID와 서비스 URL을 등록하면
[네이버 JavaScript 지도](https://navermaps.github.io/maps.js.ncp/docs/tutorial-2-Getting-Started.html) 위에 현재 보행 경로를 표시하는 방식으로 바꿀 수 있습니다.
현재는 사용자 선택에 따라 키가 필요 없는 OSM 배경만 연결합니다.

검증: 추천 API·실제 9곳·거리 비교 회귀 테스트 **38개 통과**.
Edge에서 실제 지도 타일·출처·구간 표시, 식당 전환, 확대/전체 경로, 접기/다시 열기,
추가 후보 경로, 다음 수업 없음(2마커), 추정 점선, 390px 모바일을 확인했습니다.
타일 요청을 차단한 뒤 도식 표시와 재시도 복구까지 통과했고 JavaScript 오류는 없었습니다.
