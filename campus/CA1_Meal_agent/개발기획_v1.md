## 1. 현재 상태 진단

| 항목 | 상태 | 의미 |
|---|---|---|
| 기능 정의서 | CA1 요구사항 약 45개 · 화면 11개 · API 9개 — 매우 상세 | 정의는 충분하다. **문제는 범위**다 |
| 코드 | `campus/` 안에 README 와 스키마만 있고 코드 0줄 | 정의서 주차 계획(9주차 규칙 추천 시제품)보다 늦다 |
| 의존하는 공통 부분 | `server/`(기기 등록·날씨·건물 마스터) · `mobile/`(PWA) 모두 미착수 | 공통 부분을 기다리면 CA1 이 막힌다 |
| 남은 기간 | 오늘(11/11, 약 10주차) → 기말(15주차) **약 5주** | 3명이 정의서 전체를 만들기는 어렵다 |
| 오늘 맥락 스키마 | v1 확정(`shared/schema/daily-context.schema.json`) | 공강 계산의 입력은 이미 고정됐다 → 바로 개발 가능 |

**결론**: 이미지가 정의서보다 훨씬 작고 선명하다. **이미지를 MVP 범위로 삼고**, 정의서의 나머지는 `나중` 으로 미룬다. 그리고 공통 서버·앱을 기다리지 않도록 CA1 은 **혼자 돌아가는 파이썬 패키지 + FastAPI 라우터**로 만든다.

## 2. 이미지 기능 분석 — 유지 / 수정 / 제외

### STEP 1 무엇을 보나

| 이미지 항목 | 판단 | 이유 · 바꿀 점 |
|---|---|---|
| 공강 길이 · 다음 강의실 건물(오늘 맥락) | **유지 (핵심)** | 이 기능이 일반 맛집 앱과 다른 유일한 이유 |
| 대략 위치 · 예산 · 취향(폰) | **유지** | 위치는 1차에 **건물 선택만**, GPS 반올림 좌표는 2차 |
| 날씨(서버) | **축소 유지** | 비 예보면 거리 가중치 ×2 하나만. 날씨 API 는 서버팀 몫이라 CA1 은 `rain: bool` 입력만 받는다 |
| 식당 · 학식(서버) | **유지** | 단, 수량 목표를 낮춘다(4절) |

### STEP 2 다녀올 수 있나

| 이미지 항목 | 판단 | 이유 · 바꿀 점 |
|---|---|---|
| `필요 시간 = 왕복 + 대기 + 식사` | **수정** | 정의서에는 **여유 5분**이 더 있다. 이미지 예시(42분)와 정의서 예시(48분)가 다르므로 **여유 5분 포함으로 통일**한다 → 이미지 예시는 `왕복 12 + 대기 5 + 식사 25 + 여유 5 = 47분 ≤ 100분` |
| `필요 시간 ≤ 공강인 곳만 남김` | **유지** + `빠듯`(5분 이내 초과) 표시 | |

### STEP 3 순위 매기기

| 이미지 항목 | 판단 | 이유 · 바꿀 점 |
|---|---|---|
| 1차 규칙 점수(거리·가격·취향·날씨) | **유지 (핵심)** | 이유 칩을 그대로 뽑을 수 있다 |
| 2차 사용 기록으로 가중치 학습 | **제외 → 선택 실험** | 5주 안에 팀원 몇 명의 2주 기록으로는 로지스틱 회귀가 의미 있는 표본을 얻기 어렵다. 발표에서 "학습"을 보여 줄 것은 **폰의 취향 학습(지수이동평균)** 으로 충분하다. 시간이 남으면 시뮬레이션 데이터로 오프라인 비교만 한다 |
| 정의서의 f_혼잡 · f_평판 | **1차 제외** | 평판은 익명 피드백 수집(옵트인 서버 저장)이 있어야 하고 표본도 없다. 혼잡은 학식 피크 대기 시간에 이미 반영된다 |

### STEP 4 추천 3곳 + 이유

| 이미지 항목 | 판단 | 이유 · 바꿀 점 |
|---|---|---|
| 이유 칩(`도보 3분` `왕복 35분` `7천 원대` `혼밥 OK`) | **유지 (핵심)** | 점수 기여 상위 요소에서 자동 생성 |
| 말로도 요청 | **유지, 순서 바꿈** | **규칙 파서를 먼저** 만들고(평가셋 대부분을 처리), LLM 은 규칙 파서가 못 푼 문장에만 쓴다 → LLM 장애·비용에 강하다 |

### 하단 카드

| 이미지 항목 | 판단 | 이유 · 바꿀 점 |
|---|---|---|
| AI의 역할: 문장 → JSON, 이유 한 줄 | **유지** | 이유 한 줄은 **템플릿 문장을 기본**으로, LLM 문장은 검증 통과 시에만(칩·속성에 없는 단어가 있으면 버림) |
| 데이터: 상가정보 + 팀 현장 조사 | **유지** | 상가정보는 API 대신 **파일 내려받기(CSV)** 로 시작 — 신청·승인 대기가 없다 |
| 학식: 생협·생활관 협조 요청 | **유지 + 대비책** | 협조가 늦어지면 팀이 주 1회 JSON 으로 입력 |
| 평가: 지각 0건 | **유지** | 단, 실사용 대신 **시나리오 시뮬레이션 + 실측 10경로**로 증명(5절) |
| 평가: 조건 해석 정확도 90% | **유지** | 평가셋 50문장 |
| 평가: 취향 학습 뒤 선택 비율 상승 | **수정** | 실사용자 수가 적어 통계가 안 나온다 → **가상 사용자 시뮬레이션**(선호를 가진 가상 사용자가 피드백 → 상위 3 적중률 변화)으로 보이고, 팀원 사용 기록은 보조 자료로 |

### 정의서에서 이번 범위에서 빼는 것

| 정의서 항목 | 처리 | 이유 |
|---|---|---|
| 관리자 웹(CA1-S10 · S11 · R70~R72) | **제외 → 파일 + 스크립트** | 식당 속성·학식은 저장소의 CSV/JSON 으로 관리하고 git 커밋이 검증자·검증일 기록을 대신한다. 화면 하나 만드는 비용을 아낀다 |
| 푸시 알림(R60~R62) | **제외** | 서버 푸시 인프라가 먼저 필요하다. 시연에 꼭 필요하지 않다 |
| 카카오 로컬 실시간 중계(R14 선택) | **제외** | 상세 화면은 카카오맵 **검색 링크**만 연다(API 키 불필요) |
| `다녀왔어요?` 시간 보정(R24) | **제외** | 대신 실측 10경로로 도보 계수를 한 번 보정 |
| 신고 큐 · 3건 자동 제외(R15) | **축소** | 신고는 받기만(파일/로그) — 처리는 팀이 데이터 파일을 고친다 |
| 분기마다 폐업 의심 비교(R10 일부) | **제외** | 학기 안에 분기가 한 번도 안 바뀐다 |
| 옵트인 익명 피드백 서버 전송(R54) | **제외** | 2차 학습을 뺐으므로 필요 없다 |
| `내일 점심` · `시험 끝나고 5명이서`(R42 · R43) | **축소 유지** | `after_block(exam)` 과 인원 → 좌석 필터는 규칙만으로 되므로 넣되, 모호한 문장 되묻기는 `점심/저녁` 한 종류만 |

## 3. 새로 추가할 기능 (제안)

"다녀올 수 있나"라는 이 기능의 존재 이유를 **더 강하게** 만드는 것만 골랐다.

| # | 기능 | 내용 | 왜 | 비용 |
|---|---|---|---|---|
| **N1** | **출발 마감 시각** | 카드에 `12:48까지 식당에서 나오면 13:00 수업 OK` 를 표시. 필요 시간 계산에서 역산 | "지각 0건" 목표를 사용자 행동으로 바로 옮긴다. 발표에서 가장 설득력 있는 한 줄 | 낮음 (같은 계산기) |
| **N2** | **시간 내역 막대** | `도보 4 · 대기 3 · 식사 30 · 도보 6 · 여유 5` 를 색 막대로 | 이유를 숫자로 보여 줘 "AI가 왜?" 질문에 답한다(설명 가능성) | 낮음 (응답에 `breakdown` 필드만 추가) |
| **N3** | **포장 모드** | 공강이 짧으면 `포장 가능` 식당을 `포장해서 강의실로` 로 다시 계산(식사 시간 대신 포장 대기 + 다음 건물로 바로 이동) | 30~40분 공강에서 후보가 0곳이 되는 문제를 줄인다. 실제 학생 행동과 맞다 | 중간 (속성 `takeout` 하나 + 계산 분기) |
| **N4** | **건물 ↔ 식당 도보 행렬 사전 계산** | OpenStreetMap 보행 경로로 `건물 × 식당` 도보 거리를 한 번 계산해 파일로 둔다. 없으면 `직선 × 1.3` 으로 대체 | 정문·후문·담장 때문에 직선 거리가 크게 틀리는 곳이 있다 → 지각 0건의 실제 위험 요소. OSM 은 저장 가능(ODbL) | 중간 (오프라인 스크립트 1개) |
| **N5** | **시나리오 시뮬레이터** | 시간표 시나리오 20개(공강 30~150분, 건물 조합, 비/맑음, 시험기간) × 추천 결과를 돌려 `필요 시간 > 공강` 인 추천이 0건인지, 실측값을 넣었을 때 지각 위험이 있는지 자동 검사 | 실사용 2주 없이도 "지각 0건"을 숫자로 증명. 회귀 테스트도 겸한다 | 낮음 |
| N6 (선택) | 완화 칩 | 후보 0곳이면 `예산 +2천` `도보 +5분` `혼밥 끄기` 를 눌러 다시 계산 | 정의서 상태별 화면에 이미 있는 것. 계산기가 "무엇 때문에 빠졌는지" 개수를 함께 돌려주면 쉽다 | 낮음 |

## 4. 최종 범위 (MVP)

### 필수 (기말 시연)

1. 오늘 맥락 → 식사 공강 계산 (CA1-R01) / 직접 입력 (R02)
2. 필요 시간 · 적합/빠듯/제외 판정 (R20 · R21) + **N1 출발 마감 시각** + **N2 시간 내역**
3. 영업시간·브레이크 확인 (R13)
4. 규칙 점수(여유·예산·취향·거리, 비 오면 거리 ×2) · 반드시 빼는 조건 · 상위 3곳 카테고리 다양성 · 이유 칩
5. 학식 카드(같은 시간 계산)
6. 말로 찾기: 규칙 파서 → (실패 시) LLM → 스키마 검증
7. 폰 취향 학습: 👍 👎 `여기 갈게` `다시 안 보기` → 지수이동평균
8. `/v1/meal/recommend` 하나가 유일한 계산기 (CA2 `recommend_meal` 도 이것을 부름)

### 권장

- N3 포장 모드 · N4 보행 경로 행렬 · N6 완화 칩 · LLM 이유 한 줄

### 데이터 목표 (낮춤)

| 항목 | 정의서 | 제안 | 이유 |
|---|---|---|---|
| 식당 현장 조사 | 11주차 60곳 · 기말 100곳 | **11주차 30곳 · 기말 60곳** | 공강에 다녀올 수 있는 반경(도보 10분 안)에 실제로 의미 있는 곳은 수십 곳이다. 수보다 **영업시간·가격 정확도**가 지각 0건에 중요하다 |
| 학식 | 최소 1곳 한 주 | 동일(학생식당 1곳 + 가능하면 생활관) | |
| 건물 | 서버 마스터 | 광주 캠퍼스 주요 건물 20~30개 — **서버팀 전에 CA1 이 seed 파일을 먼저 만들고 넘긴다** | 막히지 않게 |

## 5. 설계

### 폴더 구조

```
campus/CA1_Meal_agent/
├── meal/                     파이썬 패키지 (학사 폴더 import 금지)
│   ├── models.py             pydantic: Place · PlaceAttr · MealQuery · TasteSummary · Candidate · Breakdown
│   ├── settings.py           유형별 식사·대기 · 도보 계수 · 가중치 · 식사 시간대 (JSON 설정, 코드에 박지 않음)
│   ├── slots.py              DailyContext → 식사 공강 목록
│   ├── walk.py               도보 분: 사전 계산 행렬 → 없으면 haversine × 1.3 ÷ 70
│   ├── hours.py              도착 시각 기준 영업 여부
│   ├── timing.py             필요 시간 · 판정 · 출발 마감 시각 · 시간 내역
│   ├── ranking.py            빼기 조건 → 점수 → 다양성 → 상위 3 + 빠듯 + 제외 사유 집계
│   ├── reasons.py            이유 칩 · 템플릿 이유 문장 · LLM 문장 검증
│   ├── query/rules.py        규칙 파서 (금액·인원·종류·혼밥·시각 키워드)
│   ├── query/llm.py          OpenAI 호환 호출 + 스키마 검증 (LLM_MAIN_* 환경변수)
│   ├── taste.py              EMA 갱신 규칙 (앱이 같은 규칙을 TS 로 복사 — 테스트 벡터 공유)
│   ├── data.py               data/ 읽기 + 버전(ETag)
│   ├── service.py            recommend() — 유일한 계산기
│   ├── api.py                FastAPI APIRouter (/v1/meal/…) — 서버팀이 include 만 하면 됨
│   └── __main__.py           CLI: python -m meal recommend --gap 100 --from 공7 --to 공2
├── data/
│   ├── buildings.seed.json   건물 seed (서버 마스터가 생기면 이전)
│   ├── places.json           상가정보에서 뽑은 후보
│   ├── place_attrs.csv       현장 조사 결과 (스프레드시트 → CSV)
│   ├── walk_matrix.json      N4 결과 (선택)
│   └── cafeteria/2026-W47.json
├── scripts/
│   ├── semas_import.py       상가정보 CSV → 음식 업종 · 반경 필터 → places.json
│   ├── attrs_check.py        조사 CSV 검증 (영업시간 형식 · 가격대 · 누락)
│   └── build_walk_matrix.py  OSM 보행 경로 (선택)
├── eval/
│   ├── queries.jsonl         문장 50개 + 정답 MealQuery
│   ├── scenarios.jsonl       시간표 시나리오 20개 (N5)
│   ├── run_parse_eval.py     필드별 정확도
│   ├── run_scenarios.py      지각 위험 0건 검사
│   └── taste_sim.py          가상 사용자 취향 학습 시뮬레이션
├── tests/                    pytest — 정의서 예시 값이 그대로 테스트
└── .env.example
```

- **공통 서버와의 경계**: CA1 은 `APIRouter` 와 `recommend()` 함수만 내놓는다. 서버팀은 `app.include_router(meal.api.router)` 한 줄로 붙인다. 날씨는 요청 안의 `weather` 값 또는 서버가 넣어 주는 함수로 받아, CA1 이 날씨 API 를 직접 부르지 않는다.
- **앱과의 경계**: 식사 화면(`mobile/`)은 공통 폴더라 PR 승인이 필요하다 → 화면 담당은 API 응답 예시(JSON 고정 파일)로 먼저 화면을 만들고, API 가 나오면 붙인다.

### `/v1/meal/recommend` 응답 (정의서 + 추가 필드)

```json
{
```
